# Pixel Office — CLAUDE.md
 
A Discord/Gather-style collaboration space rendered as a 2D pixel-art office.
Players sign in, walk around a shared tile map, and (later) chat and talk by proximity.
 
## Team
 
- 2 people. Dyg owns the backend, realtime server and infrastructure. The teammate owns the UI.
- Work is spec-driven. Nothing is implemented without an approved spec and a plan.
## Repository layout
 
```
specs/<feature-slug>/     spec.md → plan.md → tasks.md (one folder per feature)
server/PixelOffice.API/   .NET 10 solution: PixelOffice.API (Web API, later SignalR hub + EF Core),
                          PixelOffice.AppHost, PixelOffice.ServiceDefaults, PixelOffice.API.Tests
app/                      Next.js (App Router) + PixiJS + TypeScript client
  src/app/                App Router routes, layout, global styles
  public/                 Static assets (sprite sheets go in public/assets)
docs/                     Architecture notes, ADRs
claude.md                 This file
```

One git repository at the project root (github.com/my-ai-projects-2026/office-pixel) holds everything: `server/`, `app/`, `specs/`, `docs/`. Hub contract changes touch `server/` and `app/src/contracts` in the same PR. Keep `specs/` and `docs/` at the root alongside `server/`.
The client currently uses `src/app/` only; add `src/` subfolders (store, net, game, contracts) as features land.
`app/AGENTS.md` is generated by `next dev`: this Next.js version has breaking changes, so read `app/node_modules/next/dist/docs/` before writing Next.js code.
 
## Stack (decided)
 
| Layer | Choice | Notes |
|---|---|---|
| Client | Next.js (App Router), React, TypeScript | Pixi canvas is a client-only component (`dynamic(..., { ssr: false })`) |
| Rendering | PixiJS v8 | Game loop and sprite state live outside React state |
| Realtime | ASP.NET Core SignalR, MessagePack protocol | One hub, one group per room; WebSockets transport only |
| API / auth | ASP.NET Core minimal API, JWT bearer | Hub authenticates with the same JWT; player identity comes from the token, never the client |
| Data | EF Core 10 + PostgreSQL | Persist accounts, avatar choice, maps, diagnostic records only |
| Live state | In-memory per server instance | Redis backplane + Redis state when scaling past one instance |
| Maps | Tiled (JSON export) | Layers: floor, walls/collision, spawn, zones |
| Voice/video (later) | LiveKit | Server issues tokens; browser connects to LiveKit directly |
| Local orchestration | Aspire 13.6 (AppHost + ServiceDefaults) | AppHost runs PostgreSQL in Docker (data volume) and injects `ConnectionStrings:pixeloffice` into the API; it also runs the client (`npm install` + `npm run dev`), passing `NEXT_PUBLIC_API_URL` to it and the client's address to the API as its only CORS origin; ServiceDefaults adds OpenTelemetry and `/health`, `/alive` (Development only). Dev-time only; tests do not run through the AppHost |
 
Do not add alternatives to this table (Colyseus, Socket.IO, Phaser, Prisma) without an ADR in `docs/`.
 
## Spec-driven workflow
 
1. `/sdd-spec` — write or update `specs/<slug>/spec.md`. No code, no framework names. Stop and wait for "approved".
2. `/sdd-plan` — turn the approved spec into `plan.md` and `tasks.md`.
3. `/sdd-implement` — implement the next task from `tasks.md`, with tests, against the spec and plan.
Rules:
- IDs (US-xx, BR-xx, AC-xx) are never renumbered. Removed items are struck through with a reason.
- Every acceptance criterion maps to at least one automated test, named `AC_xx_...` on the server and `AC-xx` in the test title on the client.
- A pull request references the task ID and the ACs it satisfies.
- If a task reveals a gap in the spec, stop, update the spec (update mode), get approval, then continue.
## Server conventions (.NET)
 
- .NET 10 / C# 14, nullable enabled, warnings as errors.
- Vertical slices by feature folder (`Features/Room`, `Features/Presence`), not by layer.
- Hub methods are thin: validate, update in-memory state, return. Broadcasting happens in a `BackgroundService` tick (10–15 Hz) that sends batched snapshots per room.
- Movement validation (speed, collision, elapsed-time budget) is pure code with no I/O, unit-tested in isolation.
- Never trust client positions. The server owns authoritative state; the client sends intent.
- Live state is never written to the database. Diagnostic records (joins, leaves, replacements, rejected moves) are persisted and purged after 30 days by a hosted service.
- Use `TimeProvider` for all time so tests can control the clock (grace periods, retention).
- Logging: structured, one event per hub call outcome, no player positions in logs above Debug.
## Client conventions (Next.js + PixiJS)
 
- `@microsoft/signalr` connection lives in a singleton module, not in React state or context.
- Game state (players, positions, interpolation targets) lives in a plain store the Pixi ticker reads directly; React subscribes only to the member list and UI panels.
- Remote players are interpolated between server snapshots; the local player uses client-side prediction and snaps to the server's correction when one arrives.
- Four-direction movement only. Most recently pressed key wins; release falls back to any key still held.
- Click-to-move uses A* on the collision grid; any movement key cancels it.
- Assets: pixel art is nearest-neighbour scaled (`scaleMode = 'nearest'`), 32 px tiles, sprite sheets in `public/assets`. Record the licence of every art pack in `docs/assets.md`.
- No `any`. Hub message types are shared with the server via a generated or hand-maintained `contracts.ts`; change both sides in the same PR.
## Testing
 
- Server: xUnit, `WebApplicationFactory` for hub integration tests, two test clients in one test to cover sync (AC-05, AC-08, AC-09).
- Client: Vitest for store, interpolation and pathfinding; Playwright for two-browser end-to-end on the first slice.
- Network conditions for AC-05 and AC-15 are simulated (Playwright route throttling or a test-only delay in the hub), never left untested.
## Commands
 
```
# server (run from server/PixelOffice.API; Docker Desktop must be running for the AppHost)
dotnet build && dotnet test
dotnet run --project PixelOffice.AppHost        # PostgreSQL + API + Next.js client (dashboard link in the output)
# Stop the AppHost with Ctrl+C so it removes its containers; killing it leaves the PostgreSQL container running.
dotnet ef migrations add <Name> --project PixelOffice.API
 
# client (run from app/)
npm run dev | npm run build | npm run lint
# planned, not defined in package.json yet: npm run test | npm run e2e
```
